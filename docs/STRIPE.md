# Stripe Connect & Payments

This document explains the Stripe integration, Connect onboarding, and payment processing logic.

## 1. Overview
The platform uses **Stripe Connect** with **Express Accounts**.
- **Platform Account**: DFWSC's main Stripe account.
- **Express Accounts**: One per connected client. Created when the client is created (`/accounts` or `/onboard-client/initiate`).

## 2. Onboarding Flow
1. **Initiate**: Admin calls `POST /api/v1/onboard-client/initiate` (or `POST /api/v1/accounts`). The API prepares a stable client ID and credentials, creates the Stripe Express account with that client ID as metadata and the Stripe idempotency key, then atomically stores the client, Stripe account/readiness state, and tokens. No database transaction is held open during the Stripe call. `/accounts` returns the plaintext `apiKey` to the admin; `/onboard-client/initiate` does **not** — it delivers the API key via an emailed link instead.
2. **Email**: Client receives an email containing two links: `/onboard#token=...` (Stripe onboarding) and `/regenerate-key#token=...` (reveals the API key once, expires in 15 minutes).
3. **Account Link**: `POST /api/v1/onboard-client` with body `{ "token": "..." }` uses the persisted Stripe account and returns an Account Link URL. A race-safe, idempotent lazy account-creation fallback remains for legacy clients whose `stripeAccountId` is null; the API does not create an Account Link until an account ID is confirmed in Postgres. Token moves to `in_progress`.
4. **Stripe Redirect**: Client completes onboarding on Stripe-hosted pages.
5. **Callback**: Stripe redirects to the platform-registered return URL, `GET /api/v1/connect/callback?client_id=...&state=...` — Stripe does **not** append `account`. `state` is CSRF-validated (32-byte, 24-hour expiry) and is the actual security binding; the client's `stripeAccountId` is looked up from the DB (source of truth). An `account` query param is accepted only as an optional legacy/manual cross-check when present. Token is marked `completed`. Browser is redirected to `/onboarding-success`. An expired state redirects to `/onboarding-success?status=expired` instead of returning an error.
6. **Refresh**: If the account link expires before the client completes it, `GET /api/v1/connect/refresh?client_id=...&state=...` generates a new link and redirects.
7. **Resend**: `POST /api/v1/onboard-client/resend` revokes all active tokens for the client and issues a new one (in one transaction) with a fresh email.

**Failure and recovery behavior.** A Stripe account-creation failure does not commit the client or expose credentials. If Stripe returned an account but the database write fails, the API attempts to delete that account; a failed deletion is logged with the client and Stripe account IDs for reconciliation. If the initiate email fails after persistence, the client and Stripe account remain, but exactly the new onboarding and API-key retrieval tokens are revoked; the admin receives `502 EMAIL_DELIVERY_FAILED` and recovers with the authenticated resend route (onboarding link) and admin API-key regeneration (API key) rather than retrying initiate. Resend returns 200 only after email delivery succeeds; a failed send revokes its newly issued token and returns the same 502 class. A token-cleanup failure returns a support-oriented error because an undelivered credential may still be active.

## 3. Payment Strategy (Stripe Checkout)
All payments go through **Stripe Checkout** — the former Stripe Elements / PaymentIntent mode and its `USE_CHECKOUT` toggle have been removed.

- Creates a **Checkout Session** with `lineItems` on behalf of the client's Express Account (direct charge).
- Returns a `url` for browser redirect to Stripe-hosted checkout.
- Line items must use inline `price_data` (no platform price IDs — those are incompatible with connected-account Checkout).
- The base amount is derived server-side from line items; a caller-supplied `amount` is ignored.
- All line items must use the same 3-letter ISO currency.
- `Idempotency-Key` header is required for all payment creation calls (both API-key and admin).
- Idempotency conflicts return 409 with one of two codes. `IDEMPOTENCY_KEY_REUSED` means the key was already used with different parameters; it is permanent, so send a new key. `IDEMPOTENCY_KEY_IN_USE` means a request with the same key is still in progress; it is transient, so retry shortly with the same key. Neither counts toward the Stripe circuit breaker.
- Other permanent Stripe errors on `POST /payments/create` are returned as 4xx instead of a retryable 502: `400 INVALID_REQUEST` (Stripe rejected a parameter; `param` names it when known) and `409 ACCOUNT_NOT_CONNECTED` (the client's Stripe account is not connected or cannot accept charges; retrying will not help). After a `400 INVALID_REQUEST`, send the corrected request with a new `Idempotency-Key`: Stripe keeps the first response for a key for 24 hours, errors included, so the old key can replay the stored error or come back as `IDEMPOTENCY_KEY_REUSED` once the body changes. These 4xx responses do not count toward the Stripe circuit breaker.
- Success/cancel URLs resolve from: client config → group config → `DEFAULT_PAYMENT_SUCCESS_URL`/`DEFAULT_PAYMENT_CANCEL_URL` if valid HTTP(S) URLs → `FRONTEND_ORIGIN` default.
- Every success URL (client, group, default or built-in fallback) carries `session_id={CHECKOUT_SESSION_ID}`: it is appended (`?` or `&`, before any `#fragment`) unless the URL already contains the literal `{CHECKOUT_SESSION_ID}` placeholder. Stripe substitutes the placeholder when it redirects the customer back. The cancel URL is unchanged.
- The 201 response is `{ url, sessionId }`. Integrators store `sessionId` against their order and confirm the result via `GET /api/v1/payments/session/:sessionId` (see below).

### Payment Ledger
Every payment creation inserts a row into the `payment_ledger` table synchronously after Stripe Checkout Session creation. The ledger tracks:
- Connected account, Stripe session ID, client, source
- Status (created → paid/expired/failed/canceled/refunded/disputed)
- Base/total/fee amounts, currency, metadata
- `last_stripe_event_created_at` for ordering protection (stale events are ignored)

`GET /api/v1/payments/session/:sessionId` returns payer-safe fields from the ledger (`status`, `baseAmountCents`, `totalAmountCents`, `feeAmountCents`, `currency`, `createdAt`; no internal IDs or metadata leaked). It is public and rate-limited to 30 requests/minute per IP. Sending the client's `X-Api-Key` authenticates the call instead: the limit becomes 600 requests/minute per client, only that client's sessions are visible (another client's session is a `404`, like an unknown one), and an invalid or inactive key is a `401`. Rejected keys are counted per client IP, once for each distinct key (30 distinct keys a minute): the same bad key repeated uses one unit. Over that budget a request with a key gets a `429` before any database lookup, except for a key that passed verification within the last minute. A rejected key keeps getting `401` for up to a minute without a lookup, so a client that was reactivated works again within a minute (at once when an admin changes its status). Integrators should fulfil only on `paid` and compare `baseAmountCents`/`currency` to their order; the public guide is the `/docs` page (Step 3).

**Stripe fallback for missed webhooks.** If the row is still `created` and older than 30 seconds, the endpoint retrieves the Checkout Session from Stripe on the row's connected account (skipped while the Stripe circuit breaker is open, but its own failures are not counted towards the breaker) and applies the same transition the webhook would: a `complete` session that is `paid` or `no_payment_required` becomes `paid`, an `expired` session becomes `expired`, and an open or unsettled session leaves the row `created`. Stripe is asked at most once per session per 30 seconds per API process. A Stripe failure or open breaker never fails the request; the stored row is returned. Reconciliation does not advance `last_stripe_event_created_at` beyond the newest event already recorded, so later webhooks still apply. The fallback cannot recover a failed delayed payment: that still needs the `checkout.session.async_payment_failed` webhook.

## 4. Fee Resolution
`application_fee_amount` is collected on every transaction via a 6-level priority chain (first non-null wins):
1. Client `processingFeePercent`
2. Client `processingFeeCents`
3. Group `processingFeePercent`
4. Group `processingFeeCents`
5. DB setting `default_fee_percent`
6. DB setting `default_fee_cents`

If none of the six levels are configured, the flat `DEFAULT_PROCESS_FEE_CENTS` environment variable is used as a last-resort fallback; if that is also unset, no fee is applied.

Pass `waiveFee: true` in the payment request body to skip the platform fee for a specific transaction. This is honored **only** for admin (JWT) payments — for API-key (client-initiated) payments, `waiveFee` is ignored and the fee is always applied.

## 5. Webhook Handling
`POST /api/v1/webhooks/stripe`
- Validates Stripe signature via `STRIPE_WEBHOOK_SECRET`.
- Deduplicates events using the `webhook_events` table (`stripeEventId` unique constraint) with a reclaimable lease mechanism.
- **Required endpoint and events**: payments are direct charges on connected accounts, so Stripe delivers these events only to a webhook endpoint registered with "Listen to events on Connected accounts" (a Connect endpoint). It must be subscribed to `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `charge.refunded`, `charge.dispute.created`, `account.updated` and, for connected-account invoicing, `invoice.finalized`, `invoice.sent`, `invoice.paid`, `invoice.payment_failed`, `invoice.voided`, `invoice.marked_uncollectible`, `invoice.updated` and `invoice.deleted`, and `STRIPE_WEBHOOK_SECRET` must be that endpoint's signing secret. Without it rows stay `created` (the status endpoint's Stripe fallback only covers completed and expired sessions).
- `checkout.session.completed` marks the row `paid` only when `payment_status` is `paid` or `no_payment_required`. For delayed-notification methods (e.g. bank debits) it arrives `unpaid`: the row stays `created` (the PaymentIntent id is still recorded) and `async_payment_succeeded` / `async_payment_failed` move it to `paid` / `failed`.
- Updates the `payment_ledger` table for: `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded/failed`, `payment_intent.succeeded/failed/canceled`, `charge.refunded`, `charge.dispute.created`.
- **account.updated ordering protection**: Retrieves current account state from Stripe rather than trusting the event payload, handling out-of-order delivery.
- Ledger updates use `last_stripe_event_created_at` to ignore stale events.

The Connect endpoint syncs connected-account invoices (see "Connected-account invoicing: webhook sync" below) and otherwise only logs: it never calls `subscriptions.*` or `subscriptionSchedules.*`, and it no longer writes `paymentsMade` metadata (removed with the dead subscription scaffolding).

### Billing endpoint (DFWSC's own clients, account level)
`POST /api/v1/webhooks/stripe-billing` (production: `https://api.dfwsc.com/api/v1/webhooks/stripe-billing`)

DFWSC bills its own clients through Stripe Customers on the **platform account** (`billing_customers`; docs/BACKEND.md sections 10 and 13). That is a different Stripe scope from Connect. A Connect endpoint ("Listen to events on Connected accounts") never receives events of the platform account, and `STRIPE_WEBHOOK_SECRET` is the signing secret of that Connect endpoint, so billing events need a **second, account-level endpoint with its own secret**, `STRIPE_BILLING_WEBHOOK_SECRET`.

- Add it in the Stripe dashboard (Developers > Webhooks > Add endpoint) with "Listen to events on **Your account**", the URL above, and exactly these events: `invoice.created`, `invoice.finalized`, `invoice.updated`, `invoice.paid`, `invoice.payment_failed`, `invoice.voided`, `invoice.marked_uncollectible`, `invoice.overdue`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `subscription_schedule.created`, `subscription_schedule.updated`, `subscription_schedule.canceled`, `subscription_schedule.completed`, `subscription_schedule.released`, `subscription_schedule.aborted`, `invoice.deleted`, `customer.deleted`. Put its signing secret in `STRIPE_BILLING_WEBHOOK_SECRET`.
- Unset secret: the route answers 404. The Client Billing mirror still works: the sweep re-reads every Customer at boot and every `BILLING_SWEEP_INTERVAL_MS` (default 1 hour).
- **Hard guard**: an event with `account` set (a connected account) answers 200 and is ignored before anything is claimed or looked up.
- Same `webhook_events` lease and dedupe as the Connect endpoint. The Customer is resolved through `billing_customers`; an unknown Customer is ignored; a known one only gets `billing_snapshots.dirty_at = now()`. The event payload is never used for data: the refresh re-reads `subscriptions.list` (`status: all`, `expand: data.schedule`), `subscriptionSchedules.list` (`scheduled: true`), `invoices.list` (no expand) and, only for open attempted `charge_automatically` invoices (at most 10 per Customer per refresh), `invoicePayments.list` (`invoice`, `limit: 10`) plus `paymentIntents.retrieve` of the latest payment's PaymentIntent (its status tells a processing automatic charge from a failed one). Only a permanent client error there (invalid request such as 404, or an unexpected object shape) is logged and makes that invoice read as failed; every other error (connection, timeout, 5xx, 429, circuit open, busy) fails the refresh, which backs off and keeps the previous snapshot. These are the only Stripe calls of the billing mirror and all are reads; a test asserts that no Stripe write method is ever called.

### Invoices and plans created from Nextcloud (DFWSC's own clients, platform account)
The "New invoice" Nextcloud Form (docs/BACKEND.md section 14) is the only place the API **creates** billing objects on the platform account. All on the platform account: no call passes `stripeAccount`, Connect is not involved. It creates, per submission:
- one-off: `invoices.create` (`send_invoice`, `pending_invoice_items_behavior: exclude`, `auto_advance: false`), `invoiceItems.create`, then (`BILLING_AUTO_SEND`, default on) `invoices.finalizeInvoice` and `invoices.sendInvoice`;
- plan: `products.create`, then `subscriptionSchedules.create` with `end_behavior: cancel`, `send_invoice` collection and one phase. On the pinned API version `2025-09-30.clover` the phase length is `duration: { interval, interval_count }` (payments x the interval); `iterations` no longer exists in the types.
Every call has the idempotency key `ncbill-{formId}-{submissionId}-{step}`; objects carry metadata `nc_form`, `nc_submission`, `client_code`. It reads (`customers.retrieve` once before a first attempt to check the Customer exists and has an email; `retrieve`, `list` and `search`, paginated, to find objects of an earlier attempt) and never updates, voids, cancels or deletes an existing object. The Client Billing mirror and its account-level webhook (above) pick the new invoices and schedules up; the request also marks the client's `billing_snapshots` row dirty.

**Runbook before the first live use.** (1) In the Stripe Dashboard confirm Settings > Billing > Invoices > "Email finalized invoices to customers" is **ON**: Stripe, not the API, emails the invoices a plan creates, and `BILLING_AUTO_SEND` does not apply to recurring plans. (2) Make the first live request a **one-off** with `BILLING_AUTO_SEND=false`, check the draft in the Dashboard, send it from there, then turn auto-send on. (3) A request whose table row shows a Stripe link exists in Stripe: finish or void it in the Dashboard, never resubmit the form. Known limits: no cap on a plan's total, and form answers must not be edited after submission (docs/BACKEND.md section 14).

## 6. Products
Products and prices are created on the **connected account** (not the platform account) by passing `stripeAccount` to Stripe API calls. Both `GET /products` and `POST /products` require a `clientId` parameter to resolve the connected account.

### Connected-account invoicing: customers
Behind `CONNECT_INVOICING=true` and the per-client `invoicing_enabled` flag, an integrator with an API key manages **Customers on its own connected account** (`/api/v1/customers`, see docs/BACKEND.md section 7). These are direct calls: every Stripe call passes `{ stripeAccount: client.stripeAccountId }` and never touches the platform's `billing_customers`. Postgres (`connect_customers`) keeps only the Stripe customer id and an opaque `externalRef` (max 100 characters, documented as non-PII: it is the integrator's own reference, never an email or name); email, name and phone live on Stripe and are never logged. Responses are a whitelisted view, never the raw Stripe object. There is no delete endpoint.

Idempotency: `POST` requires an `Idempotency-Key` (trimmed, max 255 characters). Only its SHA-256 hex is stored in `connect_customers.idempotency_key` and sent to Stripe as `<clientId>:cust:<hash>`, so a key can never park personal data in Postgres. `(client_id, idempotency_key)` is unique locally, so a repeat returns the stored customer (200) without a second create, after checking the request against it (externalRef from the row; email, name, phone and user metadata from the Stripe customer): a different body is `409 IDEMPOTENCY_KEY_REUSED`. A taken `externalRef` is a `409 CUSTOMER_EXISTS` (with the existing id) decided locally before any Stripe call. If two requests race on the same `externalRef`, the loser has already created a Stripe customer: it is deleted on a best effort on the same account (a failed delete only leaves an unreferenced customer; its id is logged) and the loser gets `409 CUSTOMER_EXISTS`. The delete is skipped if a stored row references that customer. A unique violation that is neither a same-key race nor an externalRef conflict deletes nothing and answers `503 CUSTOMER_PERSISTENCE_FAILED`, as does a non-unique insert failure after Stripe created the customer: retry with the same key, which Stripe answers with the same customer. Known limitation: a retry after Stripe's 24 hour idempotency window following such a 503 can create a second Stripe customer, leaving the first unreferenced on the account.

### Connected-account invoicing: draft invoices
`POST /api/v1/invoices` creates a **draft** `send_invoice` invoice on the client's own connected account (direct charges, like Checkout; see docs/BACKEND.md for the API). Every call passes `{ stripeAccount: client.stripeAccountId }` and runs through `withStripeCircuit`; none touches the platform account, `billing_customers` or `/webhooks/stripe-billing`.

- **Invoice.** `invoices.create` with `customer`, `collection_method: "send_invoice"`, `days_until_due`, `auto_advance: false`, `pending_invoice_items_behavior: "exclude"`, `currency: "usd"`, `application_fee_amount` (omitted when the fee is 0), optional `description` and `footer`, and metadata. No automatic tax, no `on_behalf_of` or `transfer_data`. Card only (the account defaults; no `payment_settings`).
- **Lines.** One `invoiceItems.create` per line, attached with `invoice: <in_...>`, using `quantity` plus `unit_amount_decimal` (a string of whole cents) and the caller's `description`, so quantity and unit price show on the invoice. Stripe's clover `InvoiceItemCreateParams.price_data` needs a `product`, which this API does not create; the lump `amount` would hide quantity and unit price. Then the fee item: description "Processing Fee", quantity 1, `unit_amount_decimal` = fee. Invoice total = base + fee, which is also the payer's total and the platform's `application_fee_amount`: the fee is a pass-through the payer sees.
- **Metadata keys we set** (`dfwsc_` is reserved; caller keys starting with it are rejected): on the invoice `dfwsc_client_id` and `dfwsc_idem_key` (the SHA-256 hex of the caller's key); on each item the same two plus `dfwsc_line` (`0`, `1`, ... or `fee`). They let a later retry find its own objects.
- **Idempotency keys.** `<clientId>:inv:<keyHash>:invoice`, `:line:<i>`, `:fee`. Inside Stripe's 24 hour key window a replay of a step returns the same object. A resumed create older than 23 hours (`INVOICE_STRIPE_KEY_WINDOW_MS`) with no saved invoice id first looks the invoice up on the row's account with `invoices.list({ customer, created: { gte: row.created_at - 5 min }, limit: 100 })`, paged while `has_more` up to `INVOICE_ADOPTION_MAX_PAGES` (50), and adopts the one whose `dfwsc_idem_key` AND `dfwsc_client_id` match. Running out of pages, or a page that is empty while `has_more` is true, is never read as "not found": it answers `503 INVOICE_ADOPTION_INCOMPLETE` and creates nothing; with the invoice saved but items missing it lists `invoiceItems.list({ invoice })` and adopts items by `dfwsc_line`. Only then does it create what is still missing.
- **Verification.** After the last item, `invoices.retrieve` must show: `total` and `subtotal` equal to base + fee, `currency` `usd`, `status` `draft`, and, when Stripe reports it, an `application_fee_amount` equal to the stored fee (the clover `Invoice` type does not declare that field; it is read when present). Otherwise `502 INVOICE_TOTAL_MISMATCH`; the draft stays, unsent and uncollectable, on the account. The fee can only be set while the invoice is a draft, and with no line editing the fee can never exceed the total.
- **Stripe replays errors too.** Stripe keeps the result of a keyed request for 24 hours, a 5xx included, so a step that failed with a 5xx keeps returning that error for the same key and parameters until the key expires; the API surfaces it on each retry and creates nothing. A lost response (Stripe made the object, we never saw the answer) resumes through the same key replay, with no duplicate. Edge: the invoice's `days_until_due` is part of that key's parameters. If Stripe saw the create, the response was lost, and the client's default payment terms changed before the retry, Stripe answers an idempotency error, which maps to `409 IDEMPOTENCY_KEY_REUSED` (use a new key; the earlier draft stays unsent).
- **Known gaps.** Who bears Stripe's own processing and Invoicing fees on legacy Express accounts, the branding of invoice emails and the hosted page are still to be checked in test mode before turning this on for a building. Until the invoice events are added to the Connect endpoint (runbook below), the only status updates for payments and dashboard changes come from the 30 s re-check on `GET /invoices/:id`.

### Connected-account invoicing: webhook sync
The Connect endpoint (`POST /api/v1/webhooks/stripe`) keeps `connect_invoices` current when an invoice changes outside this API: paid on the hosted page, voided or sent from the Stripe dashboard, edited, or deleted. Implementation: `lib/connect-invoice-sync.ts`.

- **Events**: `invoice.finalized`, `invoice.sent`, `invoice.paid`, `invoice.payment_failed`, `invoice.voided`, `invoice.marked_uncollectible`, `invoice.updated`, `invoice.deleted`. `invoice.payment_succeeded` is also routed (an alias of `invoice.paid`) but needs no subscription. `application_fee.*` stays log-only.
- **Rules.** An event without `account` is acknowledged and ignored (a platform invoice belongs to the billing endpoint; the two handlers never act on each other's events). The row is looked up by `(stripe_invoice_id, connected_account_id)`; no row (an invoice made in the dashboard) is acknowledged. A row whose `creation_state` is not `complete` is left to the create flow. Otherwise the invoice is **re-read from Stripe** on the event's account (the payload is never trusted) and written through the same function as the `GET` re-check, so a row only moves forward (draft, open, uncollectible, paid or void) whatever order events arrive in. A 404 marks a draft `deleted`. `last_stripe_event_created_at` keeps the newest event time (`GREATEST`; diagnostic only, never used to skip an event) and `last_synced_at` is set, which also resets the 30 s `GET` clock.
- **`invoice.sent`** sets `sent_at` only when it is null and never changes `send_count` or `connect_invoice_sends`: a send from the dashboard does not count towards the API's cap of 3.
- **Errors.** An open circuit, a busy limiter, a Stripe 5xx or 429 and connection errors answer non-2xx and release the claim, so Stripe redelivers. A 401, 403, 409 or 429 also answers non-2xx (a rotated key or a lock heals, and dropping the event would lose the only push signal). Only a definite per-invoice answer is acknowledged: a 404 (marks a draft `deleted`; for a row past draft it logs a warning with the ids and status and changes nothing) and a 400 invalid request that is not about credentials (warning with the Stripe code only). Dedupe and replay use the existing `webhook_events` lease. Logs hold event and invoice ids and codes, never hosted URLs, PDF links, emails or Stripe messages.

**Runbook (manual owner step, NOT done yet).** Before turning `CONNECT_INVOICING` on for a building:
1. In the Stripe dashboard open Developers > Webhooks and select the **existing Connect endpoint** (the one set to "Listen to events on **Connected accounts**", whose signing secret is `STRIPE_WEBHOOK_SECRET`). Add exactly these 8 events: `invoice.finalized`, `invoice.sent`, `invoice.paid`, `invoice.payment_failed`, `invoice.voided`, `invoice.marked_uncollectible`, `invoice.updated`, `invoice.deleted`. No new endpoint or secret. Do **not** add them to the billing endpoint.
2. Verify in test mode: create and finalize a draft through the API for a test-mode connected account, then pay it from `hostedInvoiceUrl` with card 4242 4242 4242 4242. Within seconds `GET /invoices/:id` shows `paid` and the endpoint's delivery log shows `200` for `invoice.paid`. Or run `stripe trigger invoice.paid --stripe-account acct_xxx` (the dev stack has the stripe-cli service): that invoice is not in `connect_invoices`, so a `200` with a debug log and no row change is the expected result.
3. Failure modes: repeated 5xx deliveries mean the Stripe circuit is open or Stripe is down (retries are automatic). Until the events are added, the 30 s `GET` re-check is the only updater.

### Connected-account invoicing: rollout checklist (DFWSC staff)
Do these in order. The integrator-facing guide is [CLIENT_INTEGRATION.md](../CLIENT_INTEGRATION.md) ("Invoicing your customers").

1. **Test-mode run.** With a test-mode connected account, create, finalize and send an invoice and pay it from `hostedInvoiceUrl` (card 4242 4242 4242 4242). Check and write down:
   - who pays Stripe's own processing and Invoicing fees on that account type (the connected account or the platform);
   - the branding of the invoice email and hosted page (account name, logo, colors);
   - that the application fee shows up in the platform balance (Dashboard > Balance, or the application fee on the payment);
   - what happens to pending invoice items when a draft is deleted (this API sets `pending_invoice_items_behavior: "exclude"` and attaches each item to the invoice; confirm no stray pending items remain on the customer after `DELETE /invoices/:id`).
2. **Webhook events (owner step).** In the Stripe dashboard, add the 8 invoice events to the existing Connect endpoint (see the runbook above): `invoice.finalized`, `invoice.sent`, `invoice.paid`, `invoice.payment_failed`, `invoice.voided`, `invoice.marked_uncollectible`, `invoice.updated`, `invoice.deleted`.
3. **Turn the routes on.** Set `CONNECT_INVOICING=true` on the API (only the exact value `true` registers `/customers` and `/invoices`) and redeploy.
4. **Enable one client.** With an admin JWT: `PATCH /api/v1/clients/:id` with body `{ "invoicingEnabled": true }`. The client's account must also have charges enabled, or writes return `409 ACCOUNT_NOT_CONNECTED`. Start with a single building and watch the logs for `Connected-account invoicing Stripe call failed`.
5. **First live invoice.** Have that client create a small real invoice for a known customer, send it, pay it, and confirm `GET /invoices/:id` shows `paid` and the `invoice.paid` delivery shows `200` in the endpoint's log. Only then enable more clients.

To switch a client off, `PATCH` `{ "invoicingEnabled": false }`; to switch the feature off everywhere, unset `CONNECT_INVOICING` and redeploy.

## 7. Environment Variables
| Variable | Description |
|----------|-------------|
| `STRIPE_SECRET_KEY` | Stripe secret key (platform account) |
| `STRIPE_WEBHOOK_SECRET` | Webhook endpoint signing secret (the Connect endpoint) |
| `CONNECT_INVOICING` | (optional, default off) Global kill switch for the connected-account invoicing routes; only the exact value `true` registers them (otherwise 404). Each client also needs its own `invoicing_enabled` flag |
